**问题：这道门禁是概率型的，"过"和"不过"取决于运气**

`audit_hit_distribution.js` 原本：① 默认样本 **80 盘**；② 默认种子 `Date.now()`（**不可复现**）；
③ 对**点估计**硬卡 `rate > 0.8` 就 `exit 1`。

而两条规则 `career_用神被冲` / `pattern_yongshen_chong` 的**真实命中率是 73%**（n=2000 实测 1464/2000）。
在 n=80 时，73% 的估计有约 **8%** 概率显示为 >80% → **门禁随机失败**（实测裸跑曾 `exit 1`）。
CI 之所以一直绿，是因为它写的是 `--sample=100 --seed=42`——**等于挑了一个能过的样本**，
把失败概率压到约 5% 而已。更矛盾的是：工具自己的注释写的是"**>80% 需人工复核**"，
代码却让构建失败（复核 ≠ 让 CI 红）。

**修法（工具侧，三处）**

1. **阈值分层**：`≥90%` → 失败（几乎必然无条件）；`80%~90%` → **仅警告**（提示人工复核）；
   `100%` 仍为硬失败。并在样本 <300 时提示"该区间波动大，建议 `--sample=2000` 复核"。
2. **默认种子固定 42**（可复现）；要换一批样本用 `--seed=random`。报告里打印**初始**种子
   （原实现打印的是 LCG 推进后的值，无法复现）。
3. **默认样本 80 → 300**，使点估计稳定。

**CI 侧**：审计步骤从 `--sample=100 --seed=42` 改为**跑裸命令** `node tools/audit_hit_distribution.js`
—— 与客户拿到交付包后跑的完全同一条路径，不再靠特殊参数"校准到能过"。

**复核结论**：改后裸跑连跑 10 次 **10/10 通过**（同一份数据、种子固定、样本 300）；
`--sample=2000` 复核确认那两条规则稳定落在 73%，80%~90% 区间为空 → **它们不是"坏规则"，
原判定确系小样本噪声**。

**仍留在台账上的一条内容观察（未改动，需命理判断）**：`career_用神被冲` 与 `pattern_yongshen_chong`
真实命中 73%，意味着约七成用户的报告里会同时出现"格局破损、运势起伏大"与"事业多波折反复"。
放在**付费报告**里，这两个板块的区分度较低且表述偏负面。是否收紧 `yongShenChong()` 的判据
（当前要求 ≥2 处冲克合证据）属内容决策，本版**不动**，仅记录数据供决策。

**验证**：14/14 回归套件 PASS + 7 道门禁 + 裸命令审计全绿；`ui/index.html` 与 `rules.json` 未变。

**为什么需要**

引擎里有三张**手工维护**的大表，任一字符写错都会**静默算错盘**，而 14 套回归套件全都碰不到它们：

| 表 | 规模 | 写错的后果 | 历史事故 |
|---|---|---|---|
| `CITY_LON` | 724 城经度 | 真太阳时校正量错 → 时柱（偶尔日柱）错 | **真发生过**：「津市市」以去"市"后的"津市"命中"天津市"，键长更长导致天津市经度被解析成 111.9°（正确 117.2°），偏 21 分钟 |
| `LUNAR_INFO` | 1900-2099 十六进制 | 一个月长写错 → 该年之后日期整体错位 | — |
| `JIEQI.data` | 1895-2100 × 12 节 | 月柱分界错 → 可能整体换柱 | — |

**判据（已用当前数据校准，零误报）**

- **城市经度**：724 键逐个"喂回 `solarCorrection`"必须解析回自己的经度（防"天津被解析成津市市"类）；
  经度落在 70~140°E；**35 个知名城市与权威坐标误差 ≤ 0.8°**。
  两者缺一不可——只验自解析是**不够的**：把一个值整体改错，它依然"自己等于自己"（自检里的注入故障 ① 就是专门证明这一点）。
- **农历表**：闰月 ∈ [0,12]、闰月天数 ∈ {0,29,30} 且与闰月有无一致、月长 ∈ {29,30}、年长 ∈ [353,385]、
  春节落在 1/21~2/21 且逐年递增（间隔 ∈ [353,385]）、**逐月首日递推自洽**（本月首日 − 上月首日 = 上月天数
  [+ 闰月天数]）、月内日期偏移自洽、6 个权威春节真值 + 7 个权威闰月真值。
- **节气表**：206 年连续、每年恰好 12 项、月份序列必须精确为 `02..12,01`（第 12 项小寒属次年 1 月）、
  格式 `MM-DD HH:MM`、年内 02→12 严格递增。

**`--self-test`：证明这道门禁不是空转的**

向三张表注入 4 处故障，要求检查器**必须报错**（跑完自动还原）：

```
✅ 经度值被改错（天津 117.2 → 111.9，即历史真实事故）
✅ 闰月字段被写坏（2000 年 leapMonth → 15）
✅ 月长位被翻转（1900 年某月 30↔29）
✅ 节气少一项（1990 年删掉第 4 项）
```

CI 里两步都跑。理由见坑 #94：**门禁最大的风险不是漏检，是"永远不会失败"**——判据写错了它照样绿。

**过程中修掉的两个"我自己的判据 bug"**（记此以免重犯）：
① 天差用 `new Date(y,m-1,d)` 算 → 1900 年上海是 **LMT +08:05:43**（IANA tzdata），算出 `14.0039699…` 天，
看起来像"数据错一天"，实际是判据引入了时区偏移 → 改用 `Date.UTC`；
② 闰月年的"月末日"检查用了 `prevExpect`（此时已被改写为闰月天数）去查正常月 → 假报错 131 处 →
改为一律取 `monthDays(y, m)`。

**验证**：14/14 回归套件 PASS + **7 道门禁**（含数据表门禁与门禁自检）全绿。

**为什么做这个（商业决策，不是技术洁癖）**

本项目的商业画像是"客户已有自己的排盘系统，买断语库"。因此客户**一定会手工拼 ctx**，
而《接入说明》第 1 条注意就是"十神必须以日干为基准，否则会静默少命中"——**我们警告了，却没给任何检测手段**。
实测（`_local/scan8_engine.js`，逐个删除字段）：

| 情况 | 结果 |
|---|---|
| 缺 `pillars`/`tens`/`five`/`xiYong`/`jiYong`/`special` 任一 | 抛原始 `TypeError`，**不含字段名** |
| 缺 `shenSha` / `strength` / `dayMasterFull` / `avgFive` | 静默 −32 / −13 / −12 / −12 条 |
| `tens` 整体错位 +1 / +2 / +5 / 全填"比肩" | 命中 122→120/121/140/113，**全程零报错** |

客户的结论不会是"我 ctx 写错了"，而是"你这库怎么才这么几条"——在 ¥299 + 12 个月支持的语境下，
这是**预测得到的第一个售后工单**。故在客户对接窗口内先行堵掉。

**新增 `validateCtx(ctx)` → `{ok, errors[], warnings[], expected, missing, summary}`**

- **最值钱的一条：重算十神**。用引擎自己的 `tenGod()` 从「日柱天干 + 四柱天干」推一遍，与 `ctx.tens` 逐位比对，
  报错精确到"年干 庚：应为 比肩，收到 劫财"；`expected.tens` 直接给出正确数组。
- 自洽性检查：`dayMasterFull` / `dmWx` / `dmYin` 与日柱是否一致；`monthZhi` / `dayZhi` 是否与月/日柱相符；
  `five` 五项之和是否等于 `sumFive`、是否等于 `avgFive×5`；`xiYong` 与 `jiYong` 是否重叠或含非五行元素；
  `shenSha` 项是否缺 `name`；`kongWang` 是否为 2 地支；`caiGuanPos` / `strength` / `gender` / `special.*` 取值是否合法。
- **区分 `errors` 与 `warnings`**：`errors` = 会崩或结果不可信；`warnings` = 结果可能偏差。
- **镜像兼容**：`pillars` 既接受 paipan 产出的 4 个 2 字干支字符串，也接受 `[天干,地支]` 数组（两者引擎都能正确处理）。
- **设计原则：只做自洽性检查，绝不自动补值或纠正** —— 自动补值会把错误藏起来，比报错更危险。

**`matchRules` 入口体检**

只拦"缺了必然抛 `TypeError`"的 6 个字段，抛 `err.code='CTX_MISSING_FIELD'` + `err.fields=[...]`；
`ctx` 非对象抛 `err.code='CTX_INVALID'`。**其余字段的缺失行为刻意不变**（仍按原逻辑静默降级），
不做成"全字段强制"是为了不改变既有调用方语义——完整检查交给 `validateCtx`（调用方主动选择）。

**回归**：`tools/test_engine.js` 60 → **80** 项，新增 20 项覆盖——
正常盘**零误报**（体检工具一旦误报就没人用）、十神错位被抓到且 `expected` 正确、
喜忌重叠 / 神煞缺 name / 支柱数≠4 报错、`[天干,地支]` 形状兼容、缺 `shenSha` 报 warning 且 `matchRules` 行为不变、
`validateCtx(null/{}/字符串)` 自身不崩、`matchRules({})`/`matchRules(null)` 错误码与消息可读、
合法 ctx 命中数不受入口检查影响。

**验证**：14/14 回归套件 PASS + 6 道门禁全绿；`kb/04-rules-db/rules.json` 未变。
